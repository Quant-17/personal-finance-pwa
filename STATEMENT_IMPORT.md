## PDF workflow

1. Add/reconcile the target bank or credit-card account, with the **opening date/balance before the statement's included transactions**. Do not set an end-of-month closing balance and then post all its historical transactions again.
2. Transactions → Import monthly PDF statement. Select the account and statement ending month. For an encrypted file, enter its password **before** choosing the PDF; processing is local and the password clears when reading starts. A wrong/missing password shows a retry/unlock message.
3. The app reads date-led rows from a readable PDF. Common numeric/English-month dates, bank Debit/Credit/Balance or Withdrawal/Deposit/Balance columns and card amounts/CR markers are supported. Missing years use the chosen ending month, allowing prior December in a January statement; all inferred dates need review. The supplied SBI grid prints Value Date then Post Date; its adapter uses **Post Date** for the ledger and preserves both labeled dates in local source details. It reassembles narration above/below centered date cells even when table headings are not readable. The Kotak adapter skips the printed row number, reads spaced English-month dates, uses right-aligned amount-column boundaries, and joins wrapped/next-page narration. Other layouts still need explicit date review.
4. Nothing is initially selected or posted. Verify amount/direction/date/description and assign categories. A bulk expense category is available, with per-row edits. Review credits separately: refunds/cashback are **not salary**. Transfers, EMIs and card repayments should remain excluded and use existing dedicated forms. This version does not implement automatic refund/contra-expense accounting.
5. Select reviewed valid rows, check duplicates, compare the row count and selected income/expense totals with the original PDF, and explicitly confirm the batch. Edits reset the check/confirmation. A successful import enters the existing ledger, category budgets, current/past-month spending and cash flow by each transaction's actual date. Subscription estimates remain inside the entered living budget; nothing adds them a second time. Imports do not rewrite forecasts or saved purchase assumptions.

CSV remains a secondary **Other: CSV import** disclosure. Its existing validated template, local preview and accounting behavior are preserved. No email connection is required for either import path.

## Parsing, privacy and limits

- PDF.js is already bundled with the app. A shared bounded text decoder now supports both statements and the unchanged loan-document extractor. The browser worker reads text positions; deterministic rules produce review candidates. No server parsing, paid AI/API, external font fetching, bank feed or background polling is used.
- Original files, optional passwords and raw extraction stay in memory only. They never enter Supabase, localStorage, sessionStorage, Cache Storage, logs, fixtures or screenshots. Private API responses still use no-store; the service worker only caches static assets. Lock/offline/background/sign-out unmounts the preview and aborts extraction/reads.
- Limits: 10 MiB, 60 pages, 500 detected transaction rows, one million extracted characters, 60-second parsing timeout. Passwords must be known to the owner; no password cracking. The password field clears as parsing starts; the supplied password is used only in memory for that read and is never persisted. Image-only scans have **no OCR** and fail with a clear message. Mixed/scanned or unfamiliar layouts can omit rows; **a non-empty preview does not prove completeness**. Owners must compare counts/totals against the original. Split a larger statement or enter unsupported rows manually.
- Issuer names describe targeted common patterns, **not certified coverage of every Kotak/SBI account, card or PDF revision**. After approval, the owner provided SBI and Kotak styles. These were analyzed privately using PDF.js; independent printed-cell checks confirmed transaction-anchor coverage, movement amounts, post-date selection and excluded credits. No original PDF contents, customer fields, dates, balances or amounts were copied into source, logs or fixtures. Regression tests use newly generated synthetic layouts. A revised future bank format may still require another adapter. Values/directions are never trusted without owner review.
- Amounts remain integer paise through decimal-safe parsing; balances are not automatically mistaken for expenses in recognized separate-column layouts. Unexplained multiple totals remain blank. Missing/unrecognized directions remain excluded. Narration is capped at 240 characters with source-line context available locally for review.

## Duplicate and accounting boundaries

The review calls `preview_statement_import`; confirmation calls `import_statement_entries`. Each accepts owner-scoped account, a SHA-256 file fingerprint and at most 500 `{source_row,entry}` objects. Entries contain exactly the existing date/type/paise/category/description fields. The source key is the page/line coordinate; editing classifications does not change it. Raw document/password/unknown fields are rejected by SQL.

Private source markers identify previously confirmed rows from that same file even if category/description/amount is edited later. Another PDF with the same account/date/type/amount/description matches the existing ledger regardless of category. Import rechecks under account locks and stores request-payload hashes/results so an interrupted unchanged retry cannot double post. Validation/range failure rolls back every entry, source marker and retry receipt together. Two genuine identical payments may need manual reconciliation; different descriptions/dates can evade a cross-file exact match, so review the ledger. Deleting a confirmed ledger entry intentionally does not erase its source marker and cause a later silent reimport.
